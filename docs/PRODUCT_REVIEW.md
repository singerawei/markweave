## 一、UI 布局是否合理

1. **一级工具栏缺少任务分组。** 20 个相似小图标权重近似，高频格式操作与低频来源/PDF/字号动作争夺空间。实测内容宽约 650 px，600 px 已溢出；320 px 下 Insert 菜单固定 x=200、宽 180，右侧超出 60 px。
2. **导航遮挡正文，核心状态反而隐藏。** 400 px 编辑区中，270 px 查找面板遮挡 67.5% 正文且 Esc 无法关闭；未保存数量只有屏幕阅读器可见。跨文件编辑用户难以判断当前正在改谁、保存会影响谁。
3. **样式不适应宿主。** 手动 dark 下，代码普通文字与表头近白对白；原生深色较好，但高对比主题仍有硬编码语法色。
4. **菜单与弹窗规则不统一。** 插入菜单长期悬浮，阅读宽度等轻量设置却使用模态 dialog；关闭、焦点、状态反馈各不相同，Help/About 还复用了警告条。

建议把 Paragraph/H1–H6 合并为样式下拉，列表成组，表格操作只在表格上下文出现；一级保留常用格式、撤销重做、插入及导航。字号/阅读宽度放设置，来源放可见来源提示和右键，导出按用户频率放导出菜单或允许固定。默认跟随 VS Code 主题。

**验收：** 320/400/600/900/1280 px、100%/200% 缩放下，主操作可达、菜单不越界、普通正文不横向滚动；10 名目标用户中至少 9 人能预测主要图标行为；修改后 ≤300 ms 显示来源和未保存数量。普通文字对比度目标 ≥4.5:1。宿主适配参考 [VS Code Webview UX](https://code.visualstudio.com/api/ux-guidelines/webviews)。

完整逐项清单见 [UI_AUDIT.md](review-artifacts/interaction/UI_AUDIT.md)，包含每个按钮的实测、必要性、建议位置和快捷键。以下是实际发现的主要问题。

| 问题 | 实际行为 | 优先级 | 量化验收 |
| --- | --- | --- | --- |
| 弹窗撤销改错对象 | 链接输入框 Ctrl+Z 不撤输入框，反而撤正文最后一个字符；真实宿主复现 | P0 | 链接/图片/PDF/图表/原文框各 20 次，不能改其他对象 |
| 查找/大纲阻塞长文档 | 约 3 万结果被直接挂载；改关键词时有 12.107 s 主线程任务；从 Find 切 Outline 还会隐藏面板 | P0 | 首批结果和切词 P95 ≤300 ms，结果 DOM ≤100，无 >100 ms 任务 |
| 另存为变成保存 | Ctrl+Shift+S 被 s 分支截成 save；实际写回原文件，无 Save As 对话框 | P0 | 20 次另存为不修改原文件；原生与自定义入口语义一致 |

| 复制依赖焦点 | 直接点 Copy 失败，点正文后成功；NotAllowedError: Document is not focused | P1 | 各焦点状态 20 次，OS 剪贴板 100% 一致，1 s 内反馈 |
| Fullscreen 名称不实 | 前后编辑区都为 794×752，仅增加 focus-mode、淡化工具栏 | P1 | 重命名专注模式或实现真全屏；名字和行为一致 |
| 列表/引用不能按预期切换 | List 第二次无变化；Quote 第二次变成嵌套引用，无当前状态 | P1 | 20 个切换用例符合定义；取消格式与加深层级分开 |
| 不适用按钮仍亮 | 初始无编辑块、普通段落中的表格操作仍可点但无反馈 | P1 | 每项定义无目标/正文/表格/代码/只读状态；无静默空操作 |
| 菜单无法自然关闭 | Insert 菜单按 Esc 或点击正文仍打开 | P1 | Enter/方向键进入、Esc 返回、外部点击关闭，100 次通过 |
| PDF Cancel 被校验阻止 | Margin=100 后 Cancel 无法退出 | P1 | 合法/非法/空参数各 20 次都能取消，导出消息为 0 |
| 右键与帮助不符 | Help 声称右键可定位来源；实际菜单没有 Reveal source | P1 | 帮助每个步骤都对应真实入口；来源命令可配置 |
| 隐藏弹窗残留 | Mermaid 弹窗 Esc 后仍留隐藏 dialog | P2 | 50 次打开/Esc 后残留 dialog 和定时器为 0 |

快捷键不能只检查代码里是否写了 Ctrl。保存、撤销、查找有入口，另存为和弹窗撤销有明确路由错误。粗体/斜体/行内代码在等待选区稳定的浏览器用例可工作，真实宿主快速序列还出现选区和焦点不一致，需分别回归稳定选区与快速选区，不能一概宣称有效或失效。

部分已实现组合（行内代码、Ctrl+Enter 退出代码块）没有 tooltip 提示；多数动作没有可配置的 VS Code 命令入口。应公开高频命令并设置上下文条件，检查宿主冲突后再选默认按键；低频按钮无需强行绑定。菜单焦点和状态参考 [W3C 菜单按钮模式](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/)。

## 三、C++、Protobuf 与其他代码块

26 个内容样例中：**10 个正常着色、5 个纯文本代码、11 个被误判为原文保护。** 这不是 26 门语言的支持率，同一语言换一段代码就可能改变显示路径。

| 样例 | 实际结果 | 影响 |
| --- | --- | --- |
| C++ 普通 int main | 正常高亮 | 简单演示看起来正常 |
| C++ include <vector>、泛型、数组下标 | 显示带 Markdown 围栏的原文块，复制/换行工具消失 | 典型 C++ 文档主路径有缺陷 |
| Protobuf / proto 基本 message | 有代码框，无语法高亮 | 语言未注册到当前高亮集 |
| Protobuf 字段选项 [packed = true] | 误入原文保护 | 常见语法即触发 |
| Python/JS/JSON 含数组、Rust/C# 泛型 | 误入原文保护 | 并非只有 C++ 受影响 |
| 围栏内 HTML/XML | 误入原文保护 | 代码内容不应被当作实际 Markdown HTML 检查 |
| TS/Python/JSON/YAML/SQL/Go/CSS 等基础样例 | 正常高亮 | 已有可用能力应保留 |
| CMake、未知语言、无语言 | 纯文本代码 | 未知语言回退合理；声明支持的语言应注册并测试 |

原因：includeParser 对 fence 内容仍执行不支持语法正则，误把 <T>、[0] 等当作 HTML/引用；高亮器只加载 common 集，没注册 Protobuf/CMake。应按 token 类型隔离代码内容，再明确支持语言和别名。

编辑效果也不足：激活代码后高亮消失；Tab 移到下一个 SECTION，没有缩进；新建代码块没有可视语言选择。26 个样例追加空格保存均保留原代码，因此目前证据是显示和交互缺陷，不能夸大为已经发生代码丢失。

**验收：** 26 个样例全部显示为代码区域、围栏内 HTML 不执行；cpp/c++/cxx 与 protobuf/proto 别名通过；每个承诺语言至少 5 个含数组/泛型/转义/Unicode 样例；设置语言 ≤2 个主要操作；Tab/Shift+Tab、Enter、Ctrl+Enter 的 20 个键盘用例通过；100 份 CRLF/Tab/特殊字符往返样例内容不丢、未编辑部分字节不变。截图和细节见 [CODE_BLOCKS.md](review-artifacts/interaction/CODE_BLOCKS.md)。

## 四、本机性能：普通正文快，大块与连续图表确实慢

首屏从 CustomDocument 创建计时，不含应用启动。普通场景各打开 3 次；输入为 DOM keydown 到第二个更新帧，常规每轮 100 字符，压力样例 40 字符。

| 场景 | 首屏可编辑 ms | 输入 P95 ms | 判断 |
| --- | --- | --- | --- |
| 普通 1 MB | 535–570 | 30.0–30.7 | 正文流畅 |
| 普通 5 MB | 1432–1496 | 25.9–26.7 | 正文流畅；滚动约 33 ms 帧，有掉帧 |
| 约 5 MB / 100 Include | 1439–1686 | 25.4–28.0 | 首屏和普通段落较好 |
| 约 5 MB / 500 Include | 1961–2082 | 26.1–28.2 | 能用；全部元数据到达约 5 s |
| 单个约 100 KB 代码块 | 238 | 31.8 | 本样本流畅 |
| 单个约 1 MB 代码块 | 656 | 356.0 | 明显卡顿；最慢输入 453.7 ms |
| 单个约 125 KiB 长段落 | 252 | 594.5 | 明显卡顿；最慢输入 758.4 ms |
| 1000 行表格 | 227 | 71.5 | 超过原定 50 ms 目标 |

额外的真实宿主并发测试：Mermaid 从 20 张等待到 5 张完成期间，120 字符输入 P95 为 32.7 ms，未观察到输入期长任务；因此不能把图表排队等待等同于普通正文被渲染卡住。另测 5 MB 中部/末尾各 60 字符，P95 为 26.7 / 27.5 ms，输入窗口无长任务。

大块压力场景仅测一轮，用于证明卡顿存在，不能当作稳定统计。1 MB 代码打开期还记录到 609 ms 主线程长任务。

**Mermaid：** 20 张每张仅 3 节点的小图，3 次新宿主中初始挂载的 20 图全部完成需 **16.71–17.05 s**。补测新渲染器首图 1382 ms、20 图 16512 ms；同一宿主缓存重开首图 267 ms、20 图 413 ms。首次队列延迟很明显，缓存掩盖首次体验。150 节点图首次约 1.77 s；5 MB/100 张分散图首图约 3.53 s，不能说这时 100 张全完成。

建议保留虚拟化，但解决单个块过大的输入成本。每次 docChanged 全量序列化活动块可能与排版一起形成瓶颈，需要 profile；增量/空闲处理不能牺牲保存和备份完整性。Mermaid 应复用 runtime、有限并发、视口优先、取消过期任务；重复建页和装载资源是根据代码及缓存对比推断的主要疑点，未精确分摊 CPU 成本。

| 性能验收 | 建议门槛 |
| --- | --- |
| 5 MB 打开 | 30 次：可读 P95 ≤2 s，可编辑 P95 ≤3 s |
| 输入 | 正文/代码/表格各 ≥1000 次，P95 ≤50 ms、P99 ≤100 ms |
| 20 张简单图 | 冷态首图 ≤1.5 s、可见图 ≤2 s、全部 ≤5 s；缓存全部 ≤500 ms |
| 100 KB 代码高亮 | ≤500 ms，文字先显示，不阻塞输入 |
| 大块边界 | 达不到流畅目标时明确大小限制和不会冻结页面的降级；不能隐去压力结果 |
| 滚动 | 60 s 帧间隔 P95 ≤33.3 ms，无持续 >100 ms 停顿 |
| 查找/大纲 | 5 MB / 3 万命中首批结果 ≤300 ms、切词 P95 ≤300 ms；结果 DOM ≤100，无 >100 ms 主线程任务 |
| 小子文件保存 | <100 KB，50 次 P95 ≤200 ms，只写正确来源 |
| 发布门禁 | 真实宿主 + 安装后的 VSIX，超阈值使发布失败 |

完整方法、逐轮数据、Long Task、语料初始哈希、脚本错误排除和范围限制见 [PERFORMANCE.md](review-artifacts/live/PERFORMANCE.md)。本轮使用少量样本、合成 ASCII 输入和短滚动窗口，不等同于完整发布验收。

## 五、其他仍需改进与验收的核心流程

| 方面 | 问题或证据不足 | 验收 |

## 六、实施顺序

1. 先修错误行为、长文档导航冻结与常用代码显示：弹窗历史、另存为、只读约束、查找/大纲虚拟化、C++/Protobuf 等代码识别、多文件保存预检查。
2. 再修高频体验：大块输入、Mermaid 首次队列、复制、PNG、菜单取消、来源/保存反馈。
3. 重整界面：样式与列表分组、表格上下文工具、自适应导航、宿主主题、可发现与可配置快捷键。
4. 用安装包、真实 IME、共享来源生命周期、PDF 视觉矩阵和多轮性能建立稳定版门禁。

已有来源模型与按需渲染值得保留，暂不建议整体重写。先用原型验证连续编辑和大块策略，再确定局部重构。此次交付的是评估、可复跑诊断脚本和证据，尚未修复产品功能。
