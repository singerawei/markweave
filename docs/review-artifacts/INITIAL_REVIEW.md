# MarkdownUP 产品评估与量化验收建议

评估日期：2026-11-01。对象：本地工作区的 MarkdownUP 0.2.0 开发版。

**判断：项目有清晰且值得保留的价值，但当前更适合受控内测。公开稳定版应优先补齐连续编辑、只读约束、保存反馈及发布门禁。**

核心价值是“打开一篇组合文档，直接修改子章节，只让正确的 Markdown 文件产生 Git diff”。源码归属模型、未修改内容原样保留、本地运行和按视口渲染，都围绕这个价值展开。当前最明显的落差是：视觉上是一篇文章，操作上仍是许多独立编辑块。

## 评估方法与结论边界

- 阅读 `dev.md`、README、版本说明、全部核心模块、界面主要代码、测试和 CI 配置。
- 本轮重新执行 `npm run check`：lint、类型检查、30 项核心及往返测试、生产构建全部通过。
- 本轮重新执行 `npm run test:ui`：6/6 通过。
- 使用生产 Webview bundle 和项目自带 Chromium 额外复核段落导航、全选、保存状态、查找、大纲、窄窗口与只读 Mermaid；记录在 [ux-probe.json](ux-probe.json)。
- 使用生产 `SourceRepository` 复核已知冲突下的部分保存；记录在 [model-probe.json](model-probe.json)。
- 额外脚本是诊断工具，记录当前行为；脚本成功退出不代表这些缺陷已修复。它们使用受控输入，不修改用户 Markdown。
- 本轮未重新运行真实 VS Code 宿主套件、安装包验证或真实中文输入法测试。仓库已有宿主结果仅作为历史证据，不能当成本轮实测。没有正式用户研究数据，因此不虚构满意度、留存率或成熟度评分。

下文“已复现”指额外浏览器/模型复核；“代码确认”指实现或文档明确存在；“待验证”指尚未证明用户影响程度或运行行为。**所有验收数值都是建议目标，除明确标注的实测值外，均不表示当前已达成。**

## 产品定位与需要保留的设计

首要用户建议聚焦在使用 VS Code、Git 和 AI 工具维护多文件技术文档的人：架构设计、接口说明、技术教程、长篇方案。先完成“阅读 → 改一段 → 保存 → Git 检查”的高频闭环，再逐步降低新用户门槛。

值得保留的已有实现：

1. Source Ownership：重复引用共享来源，编辑后只写正确文件，当前核心与界面测试已有覆盖。
2. Git 友好：未修改块保留原文和换行风格，不理解的语法保留为原文块。
3. 外部编辑协作：有版本检查、冲突提示与差异查看，适合 AI/文本编辑器共同修改的场景。
4. 离线与性能架构：本地资源、严格 CSP、Include 路径边界、分批传输和单活动编辑器，方向合理。

以上是已有实现及有限测试支持的优势，并非对所有语法、文件系统和故障场景的完整保证。

## 优先级与改进清单

P0：进入公开稳定版前必须解决，直接影响核心写作流程、用户对模式的信任或发布可靠性。

### R01 · P0 · 从“块内编辑”变成真正的连续写作

**已复现：** 同一源文件两个普通段落，第一段末尾按 ↓ 再输入 `Q`，字符仍追加在第一段；第二段开头按 Backspace 不会合并上一段；活动段落内 Ctrl+A 只选中该块。见 [编辑截图](editing.png) 和 `ux-probe.json`。

**证据：** `src/webview/editor.ts:100` 每次只激活一个分段 EditorView；`:175` 附近未提供跨分段光标移动。README 的跨块限制不只影响跨文件操作，也会影响普通单文件写作。

**建议：** 保留来源模型和虚拟化，在其上实现连续光标与选择模型。同源相邻段落可以正常合并、拆分；跨源读操作连续，跨源写操作有明确规则。不要把内部 SourcePiece 边界变成用户必须理解的操作单位。

**验收：**

- 为相邻段落、标题、列表、表格、代码与 Include 边界建立不少于 30 个交互用例，方向键、Shift+方向键、Home/End、Backspace/Delete 全部符合定义；同源相邻段落导航与合并 100% 通过。
- Ctrl+A 与复制支持完整组合文档，包括未挂载内容；导出的纯文本无遗漏、重复或错误工具栏文字，100 份样本全部通过。
- 跨来源写入若暂不支持，应在写入前明确阻止且保留选择和原内容；不得先删一部分再报错。跨来源光标移动和复制不受此限制。
- 10 名目标用户完成“改标题、合并两段、移动到下一章再修改”的任务，至少 9 人无需源码模式完成。

### R02 · P0 · 只读模式必须覆盖所有修改入口

**已复现：** More → Read-only preview 后，仍能通过 Mermaid 的 Edit → Apply 修改图表；前端实际发出 1 条 `edit` 消息，节点从 A 变为 Changed。

**证据：** `src/webview/editor.ts:101` 只在 `activate()` 检查只读；`update()` 和 `src/webview/enhancements.ts` 的图表修改回调没有同样约束。宿主接收编辑消息时也没有核验该面板的只读状态。

**建议：** 统一所有修改入口的模式检查；只读状态清晰可见，修改按钮禁用或隐藏。异步打开的对话框也应在提交时重新检查模式。

**验收：** 普通文字、原文块、任务勾选、格式化、插入、粘贴、拖放、Mermaid 及“打开弹窗后切换只读再提交”共至少 100 次操作，产生的修改消息数、模型内容变化数和磁盘内容变化数均为 0；恢复编辑模式后操作正常。另行明确撤销/重做是否允许，并按同一规则实现和测试。

### R03 · P0 · 多文件保存要先检查，并准确报告结果

**已复现：** 主文档和子文件都有修改，子文件已经被标记冲突。调用保存后，主文档先被写入，随后才因子文件冲突失败。结果是“主文档已保存，子文件未保存”，并非所有文件都未保存。

**证据：** `src/document/sourceFile.ts:102` 按文件逐一检查并写入；[模型复核结果](model-probe.json) 中 `writes` 包含 MASTER.md，子文件仍 dirty。README 已诚实声明保存不具备跨文件事务能力；问题是缺少保存前整体检查和用户可见的逐项结果。

**建议：** 对本次所有待保存文件先检查已知冲突、磁盘版本和可检查的写入条件，再开始写入；对实际 I/O 中途失败，明确展示已保存、失败、尚未尝试的文件，支持重试。

**验收：**

- 注入已知冲突或检查阶段可发现的磁盘版本差异时，保存批次写入次数为 0。
- 在第 1/2/末个文件写入时注入权限变化、磁盘满或进程退出，各执行 20 次；已完成的写入状态可识别，未完成内容可恢复，不能统一提示“全部已保存”。
- 正常路径修改一个子文件时，其余文件字节与修改时间不变；100 次回归全部通过。
- 重试仅处理未成功文件；所有文件成功前保留相应未保存提示。

这不要求承诺通用文件系统上的跨文件原子事务，也不能把预检查描述为完全消除并发竞态。

### R04 · P0 · 把性能目标落实为可失败的发布门禁

**代码确认：** `dev.md` 已定义性能 Release Gate；`.github/workflows/ci.yml` 没有执行 `test:host`。`tests/integration/vscode.ts:95` 附近会记录宿主性能，但没有对这些时间阈值做断言。前端 benchmark 只在第一个可编辑块中注入字符，不能代表大表格、大段落或中文输入。

**历史证据：** 仓库 `bench/results/vscode.json` 在 2026-11-01 的记录中，1 MB 首屏可读 269 ms，5 MB 首屏可编辑 2067 ms，5 MB/100 Include 首屏可读 233 ms。这些是一次既有宿主运行结果，计时不包含 VS Code 应用启动；不是本轮重新测得，也不是多轮 P95。

**建议：** 安装后的 VSIX、真实宿主、固定语料和阈值共同构成发布门禁；报告绑定版本与构建哈希。保留快速浏览器测试作为提交检查。

**验收：** 在记录 CPU/内存/SSD/系统/VS Code 版本的基准机上，每场景独立打开 30 次，以打开时间 P95 判定：

| 场景 | 建议门槛 |
| --- | --- |
| 1 MB，从打开编辑器请求到首屏可读 | P95 ≤ 1.5 s |
| 5 MB，同一计时起点到首屏可读/可编辑 | P95 ≤ 2 s / 3 s |
| 5 MB / 100 Include，首屏可读 | P95 ≤ 2 s |
| 500 Include，首屏可读/可编辑 | 建议新增 P95 ≤ 2 s / 3 s |
| 输入事件到更新帧 | 每类场景至少 1000 次输入，P95 ≤ 50 ms |
| 修改单个 <100 KB 子文件后保存 | 50 次，P95 ≤ 200 ms |
| 连续滚动 60 s | >100 ms 主线程任务不超过 1 次，无 >500 ms 任务 |

- 输入位置必须包括正文中部、末尾、大表格、≥100 KB 单代码块/段落及 Include；不能只测第一个标题。
- 单独记录应用冷启动、编辑器首屏、全文索引完成和首图完成，避免用首屏速度掩盖后续等待。
- 每个发布候选至少一次安装后真实宿主验收；人为把一项阈值调低后，流水线必须失败。若托管 CI 的硬件不稳定，使用固定发布机完成同等阻断，不能仅上传 JSON。
- 打开/关闭 5 MB 组合文档 20 次，关闭并空闲 60 s 后的进程内存，相对预热后基线增长 ≤100 MB；图表浏览器按设计空闲退出。明确统计 Extension Host、Webview 和图表进程，不能只统计 Node heap。

### R05 · P1 · 用户应看得见“正在改谁、还没保存什么”

**已复现：** 收到 `1 unsaved files` 状态后，元素大小只有 1×1 px，且 `clip-path: inset(50%)`。状态保留给辅助技术，但普通用户看不到文件级信息。VS Code 标签页的 dirty 标记不能代替“哪些源文件会写入”。

**证据：** `src/extension/editorProvider.ts:231` 的 `#status.sr-only`；`src/webview/editor.ts:338` 的状态更新；`:67` 的来源提示使用完整 file URI。

**建议：** 工具栏或底部提供简洁状态，如“正在编辑 features/payment.md · 2 个文件未保存”；点击展开文件清单。平时不显示大边框，悬停/聚焦时轻量说明来源和重复引用影响。

**验收：**

- 修改后 ≤300 ms 出现可见未保存状态；保存成功反馈在磁盘完成写入之后、≤500 ms 内更新；失败不得变成“已保存”。
- 清单中的文件集合与模型 dirty 集合 100% 相等；两个同名文件能通过工作区相对路径区分。
- 重复引用显示“此修改会同步到 N 处”，N 与实际引用次数一致。
- 10 名目标用户中至少 9 人在 5 s 内判断当前正在修改哪个文件、保存会影响几个文件。
- 保留语义化 `role=status`；状态更新无需抢夺焦点。可参考 [W3C 状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。该标准支持辅助技术通知，并不要求把普通用户所需状态隐藏。

### R06 · P1 · Include 的日常管理不应要求手写源码

**代码/文档确认：** 可以编辑已引用内容，但新增和删除 Include 要切回 Text Editor。插入图片也要求填写路径。空白文档到组合文档的建立过程，仍依赖用户理解指令和相对路径。

**建议：** Insert 中增加“引用现有 Markdown”，用文件选择器生成相对路径；提供打开来源、替换引用、移除引用。删除操作明确区分“移除引用”和“删除磁盘文件”。缺失引用错误提供直接修复入口。

**验收：**

- 引入、替换、移除引用均在可视编辑器中 ≤3 个主要操作完成，不把打字次数算作点击；所有操作支持撤销/重做。
- 使用中文、空格、嵌套、重复引用、同名文件、循环引用、越界路径等 ≥20 个用例，合法引用 100% 正确，非法引用在写入前拒绝。
- 移除引用只更改指令所在文件，磁盘子文件内容不变；有未保存子文件时明确处理并保留其修改。
- 10 名首次使用者中 ≥9 人在 3 min 内完成“安装后打开示例 → 添加章节引用 → 修改章节 → 保存”，无需人工指导；单独记录安装耗时和网络条件。

### R07 · P1 · 查找、大纲、锚点需要形成完整导航闭环

**已复现/代码确认：** 查找结果点击后只聚焦整个块，没有选中命中词；Esc 不关闭查找。Setext 标题（下划线形式）能渲染成标题，却没有进入大纲。`#title` 链接点击被前端阻止默认行为后发送给宿主，宿主对 `#` 开头链接没有跳转分支。

**证据：** `src/webview/editor.ts:271`—查找与大纲实现；`src/extension/editorProvider.ts:133`—链接处理；复核记录中的大纲只有 `Title`，缺少 `Setext title`。

**建议：** 用同一 Markdown 结构生成标题、大纲和锚点；查找按具体命中而非源块列结果，显示数量、当前位置、来源和上下文。

**验收：**

- 覆盖 ATX/Setext、中英文、重复标题、多个引用文件与 `file.md#heading` 的 ≥30 个导航样本，跳转正确率 100%；重复标题的消歧规则有文档。
- Ctrl+F 输入后，5 MB 文档结果完成 P95 ≤300 ms；选择命中后 ≤200 ms 定位并高亮词语；Enter/Shift+Enter 遍历、Esc 关闭并恢复正文焦点。
- 全文加载完成前明确显示“正在索引”；匹配数与定义好的搜索文本基准完全一致，不能把尚未收到的内容算作“无结果”。
- 1000 个匹配结果时面板只挂载有限窗口，输入仍满足性能门槛；没有无上限的结果 DOM。

### R08 · P1 · 中文输入、撤销与恢复应成为可靠性主测试

**代码确认/待验证：** 每次正文变更都会产生一个宿主撤销事件，未见按连续输入分组；已有界面用例输入 `Adyen` 后撤销一次只删除最后一个字符。这证明当前按事务撤销，不能直接断言所有输入法都会丢字。现有文档也明确缺少真实 IME 长时间测试。

**建议：** 对连续输入设置合理撤销分组；粘贴、格式化和输入法提交各是明确事务；恢复测试必须包含磁盘同时变化、多根文档共享来源和故障后的未保存修改。

**验收：**

- 建议连续输入在 ≤500 ms 间隔内合并，停顿 ≥1 s、切换来源或执行结构操作时分组；一次粘贴和一次 IME 上屏各能一次撤销。最终分组规则固定为可测试契约。
- 使用真实 Windows 中文拼音输入法及一种额外常用输入法，每种完成 ≥1000 次提交、≥100 次取消/候选切换，丢字、重字、次序错误、撤销后残留均为 0。
- 进行至少 30 次“输入法组合中按保存/撤销/切换块/收到外部更新”，处理结果与定义一致，原始输入可恢复。
- 以 2 个主文档共享同一子文件进行编辑、撤销、保存、关闭与丢弃测试，至少 20 个交错用例，磁盘内容、所有可见面板与 dirty 状态一致。
- 保存失败、热退出、未保存内容恢复且磁盘已变、子文件被移除引用等 ≥50 个故障样本，最后一次可恢复草稿与外部版本均不被静默覆盖。

VS Code 会按扩展上报的编辑事件维护撤销栈；分组及面板同步要由扩展设计，不能把“接入了原生撤销命令”等同于已满足写作体验。参考 [VS Code Custom Editor API](https://code.visualstudio.com/api/extension-guides/custom-editors)。

### R09 · P1 · 窄窗口、键盘和语言要适应真实桌面使用

**已复现：** 在 400 px 宽编辑区，查找面板固定宽 270 px，遮挡约 67.5% 的可用宽度；见 [窄窗口截图](narrow.png)。源码中工具栏采用横向滚动，菜单位置固定。界面提示主要为英文，与中文文档的目标用户不完全一致；Help 中还残留问号分隔文本。

**建议：** 为分屏设计紧凑工具栏和可折叠导航；菜单按触发按钮定位并自动避开窗口边缘；统一弹窗标题、焦点回收、Esc 行为和中英文资源。

**验收：**

- 在 320/400/600/1280 CSS px 宽度及 100%/200% UI 缩放的组合中，主要操作可达，普通正文无需横向滚动；表格、代码与图表可局部滚动。
- 400 px 下导航默认不遮挡正文，可改为可关闭覆盖层或上下布局；Esc 关闭后正文光标位置不变。
- 仅使用键盘完成打开、导航、编辑、插入、查找、保存、处理冲突与导出；所有交互控件可聚焦、有可理解名称，无焦点陷阱。
- 常规文字对比度 ≥4.5:1，控件及焦点可视边界目标 ≥3:1；浅色、深色和高对比主题各验收一次。这里是建议产品指标，不表示本轮已完成完整 WCAG 审计。
- 支持中文/英文两套完整用户文案，关键流程未翻译项为 0；用 VS Code 语言设置选择界面语言。

正文重排的设计参考 [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)。该标准允许表格和图示等必要二维内容例外；本建议对编辑器面板可用性的要求是产品验收目标，不应直接等同于某项标准违规判定。

### R10 · P1 · 图片应融入写作工作流

**代码确认：** 图片插入弹窗仅接受文本与路径；未见剪贴板图片落盘和图片文件选择器。远程图片按设计不自动加载，不能当作缺陷；但当前只显示占位内容，用户未必知道原因。静态图片和活动编辑器的 data URI 策略也不一致。

**建议：** 支持粘贴截图、选择本地图片；明确资源保存目录和归属。对远程/丢失/越界图片分别给出可理解原因与可执行入口，保持默认离线策略。

**验收：**

- 粘贴截图 ≤2 s 出现预览，文件写入可预测的工作区资源目录，Markdown 写入正确相对路径；主文档里编辑子文件时以子文件位置为基准。
- PNG/JPEG/GIF/WebP/SVG、中文文件名、空格和重复文件名共 ≥30 个用例；支持的格式编辑与导出一致，不支持的格式明确提示。
- 大小上限和重名规则有明确设置；超过上限在落盘前告知，重复粘贴不覆盖已有文件。
- 网络断开时本地图片插入、预览、保存正常；远程占位清楚说明“未加载远程资源”并提供复制地址等不依赖网络的操作。

### R11 · P1 · PDF 要与编辑器的语义保持一致

**代码确认：** 编辑器使用自定义 `markdownTokenizer()`，PDF 使用另一个 `new MarkdownIt({html:false})`。编辑器的任务列表有专门转换，PDF 中未见同样转换，存在“勾选框在导出中退回 `[x]` 文本”的实现差异。原文保护块、跨页表格、图片和特殊字符也需要更丰富样本；本轮没有重新导出并做 PDF 视觉验证，因此这些是需验证的保真风险。

**建议：** 共享结构解析与语义转换，打印布局单独处理；导出前汇总资源问题并定位回源，避免处理到后面才告诉用户第一个错误。

**验收：**

- 固定 30 份样本，包含中英文、任务勾选、表格、长代码、Mermaid、特殊字符、重复 Include 和未保存修改；可支持元素语义一致率 100%，无正文丢失、重复、截断或页面重叠。
- 对暂不支持语法明确约定是“保留原文”还是“可视排版”，所有样本按该约定验收，不能在导出时静默隐藏。
- 有效导出中 PDF 文字可搜索；未保存子文件内容进入 PDF，源 Markdown 哈希保持不变。
- 资源检查覆盖全部引用，错误列出准确源文件与资源位置；导出失败不覆盖原有成功 PDF，取消后不残留输出临时文件。
- 1 MB 含 20 张普通图的样本导出 P95 ≤15 s，5 MB 含 100 张普通图 P95 ≤60 s，各测 10 次；统一记录图复杂度，取消响应 ≤2 s。

### R12 · P1 · 外部修改后保持阅读位置和编辑上下文

**代码确认/待验证：** 结构变化会刷新整个文档；前端只尝试在第一批 `message.segments` 中恢复活动块，同时记录的是活动块 ID 和像素 scrollY，未完整保存选择范围。100 Include 文档中，靠后的活动块未必存在于第一批 128 段里，可能丢失焦点或阅读位置。

**建议：** 使用来源 URI、稳定块标识、块内偏移和可见锚点恢复上下文；结构变更只更新受影响区域。异步追加后继续恢复，避免被第一批数据边界截断。

**验收：** 在文首/中部/末尾和未挂载区域，以外部工具进行插段、删段、修改引用、重命名文件等 ≥40 个场景；未直接受变更影响的光标偏移与选择保持，滚动锚点漂移 ≤一行正文高度；发生冲突时输入草稿仍可复制和恢复，不能只显示报错后丢掉编辑态。

### R13 · P2 · 安装、平台范围和证据版本要一致

**代码/文档确认：** 当前 VSIX 为 131,229,994 字节，约 125.2 MiB，内含 Windows Chromium；PDF/图表运行路径固定为 `.exe`。包元数据缺少 repository、author、keywords 等信息。`docs/VALIDATION.md` 仍以 0.1.0 和 4 项界面测试描述验收，当前实际是 0.2.0、6 项界面测试。

**建议：** 近期明确支持“Windows x64 本地文件”即可；其他平台和 Remote/WSL 的行为写清楚，不把跨平台当作立即阻塞项。优先保留离线安装能力；是否增加按需图表组件，应基于安装放弃率和真实需求决定。

**验收：**

- 3 个全新 Windows x64 VS Code 配置，断网安装 VSIX，完成打开、编辑 Include、保存、Mermaid 与 PDF；无需另装开发运行时。
- 非支持平台/URI 类型在进入主要流程前给出平台及文件位置说明，不让用户遇到找不到 `.exe` 的底层错误。Remote/WSL 至少分别记录支持状态。
- 发布版本、构建哈希、测试数量、语料哈希、机器信息与原始报告在同一发布清单中一致，过期版本说明为 0。
- 发布前补全真实发布者、仓库、问题反馈入口与功能截图；不代填虚构身份。
- 对安装包体积设回归预算：超过当前基线 10% 必须说明原因；安装时长在统一环境中实测后再设 SLA，不凭空承诺所有机器都能若干秒完成。

VS Code 的平台运行位置和有限工作区声明可参考 [Extension Manifest](https://code.visualstudio.com/api/references/extension-manifest)。本文未验证 Marketplace 上线状态，也没有发布外部资源。

## 建议迭代顺序

| 阶段 | 范围 | 退出条件 |
| --- | --- | --- |
| 第一阶段：稳定核心写作 | R01—R04；同时完成 R05 基础保存反馈与 R08 恢复/IME 测试 | 所有 P0 验收通过；无已知静默丢失或错误来源写入；关键故障可恢复 |
| 第二阶段：降低日常操作成本 | R06、R07、R08 剩余体验、R09、R10、R12 | 10 人任务测试 ≥9 人无需源码完成；关键写作任务无阻塞 |
| 第三阶段：交付与分发 | R11、R13 | 导出样本通过；清洁安装通过；版本证据一致 |

阶段只表达依赖关系，不凭代码体量估算工期。连续编辑模型可能是本次改进中成本最高的部分，应先做原型并同时验证来源归属和大文档性能；无需为了保持原实现而牺牲连续写作，也无需立即整体重写。

## 产品层面的成功指标

以下是建议的研究与试用指标，当前没有基线数据。以明确样本与任务计数，不把小样本比例当成全体用户统计结论。

| 指标 | 定义与建议目标 | 收集方式 |
| --- | --- | --- |
| 首次核心任务完成 | 10 名首次使用者中 ≥9 人完成打开组合文档、改子章节、保存、确认正确文件变化；每人 ≤3 min，不含安装 | 主持式可用性测试，记录失败原因 |
| 来源可理解性 | ≥9/10 人在 5 s 内正确回答“会改哪个文件” | 任务中抽查 |
| 编辑效率 | 修改标题、两段正文和一个表格并保存，比同一参与者现用的源码/预览流程中位用时降低 ≥20%，错误数不增加 | 同一文档、交叉顺序测试 |
| 保存正确性 | 固定语料与故障矩阵中错误文件写入、静默丢失、未修改内容意外重写均为 0 | 自动化 diff、哈希、故障注入 |
| 真实使用意愿 | 20 名目标用户试用两周，≥12 人在第二周至少两天使用核心编辑流程；明确记录退出原因 | 自愿访谈/本地日志导出 |

保持项目“无默认遥测”的承诺：首轮通过可用性观察、自愿反馈及用户主动导出的诊断记录测量；如未来引入统计，另行设计明确选择，不把埋点当作此轮前提。
