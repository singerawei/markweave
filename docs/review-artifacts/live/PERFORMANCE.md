# 本机真实性能评估

2026-11-01；当前生产构建，真实 VS Code 扩展开发宿主。**普通长文档正文基本流畅；连续图表和超大单块存在明确的可见延迟。**

## 环境与方法

- CPU：Intel(R) Core(TM) i7-8550U CPU @ 1.80GHz，4 个物理核、8 个逻辑处理器；RAM 15.89 GiB；Windows 10 10.0.19045；SATA SSD。
- VS Code 1.123.0，Node v20.19.6；系统显示缩放 125%；真实宿主截图中的编辑区约 794×752 CSS px。
- 本地生产 Webview SHA-256：`c8d4bcc220c2f47ab2d0cb7c4385b2c870ce06f3da652268fe1fe5dcfc74c077`。没有修改产品运行逻辑、没有 CPU 限速；使用独立 VS Code 配置和临时工作区。
- 先重新执行现有 `npm run test:host`，随后新增鼠标/键盘驱动的宿主测试。21 条完成的场景记录：4 个普通场景各 3 轮、连续 20 图各 3 轮、6 个压力场景各 1 轮。另有冷/缓存对比和真实按钮验证。
- 打开时间使用产品自身从 CustomDocument 创建到 Webview 帧回调的计时；不含 VS Code 应用启动，命令发起到文档创建的额外时间单列在原始 JSON。不能将这些数字解释为应用冷启动。
- 正文每轮输入 100 个 ASCII 字符，压力场景输入 40 个，每字符间隔 15 ms；输入延迟为 DOM keydown 到第二个 requestAnimationFrame 的时间。它包含浏览器帧调度，不能代表物理键盘扫描、屏幕实际呈现或真实中文输入法。
- 滚动使用真实 CDP mouse wheel，每轮 20 次；记录滚动窗口中的帧间隔和 Long Task。不是使用原有脚本只往第一个标题里 insertText。
- 常规打开仅 3 轮，使用范围而非把 3 次打开包装成稳定的 P95；输入 P95 来自每轮的 40/100 个输入样本。压力场景一次测量用于发现问题，正式发布仍需重复。
- 临时语料会输入并保存；同一工作区后续轮次可能保留前轮新增的约 100 个 ASCII 字符，最大体积差低于 0.01%。初始语料大小及哈希见 [fixtures.json](fixtures.json)。临时工作区之外的用户 Markdown 未被测试修改。

| includes-100.md | 3 | 136–174 | 1439–1686 | 25.4–28.0 | 33.4–33.4 | 正文输入流畅；滚动会出现约 33 ms 帧，未持续满 60 Hz |
| includes-500.md | 3 | 160–192 | 1961–2082 | 26.1–28.2 | 33.3–33.5 | 正文输入流畅；滚动会出现约 33 ms 帧，未持续满 60 Hz |

首屏快不等于全文已经可查找：5 MB 单文件全部分块元数据到达的观测上界为 3.67–3.71 s，100 Include 为 4.24–4.60 s，500 Include 为 4.92–5.04 s。这个检查含预设约 200 ms 等待和 50 ms 轮询误差，是到达时间的观测上界，不是精确的“全文渲染完成”事件。

额外测试了 5 MB 文档中部与末尾，各 60 个字符：中部输入 P95 26.7 ms、激活块 193 ms；末尾输入 P95 27.5 ms、激活块 138 ms，两者输入窗口均未观察到 Long Task。对应约第 14907 / 29808 章，证明本次正常正文结果并不只来自文首；这是一次定位后诊断，不代表跨块键盘导航已解决。见 [positions.json](positions.json)。

## Mermaid：必须区分第一张、队列末尾和缓存

| 场景 | 样本 | 首图完成 ms | 首批挂载内容完成 ms | 实际含义 |
| --- | --- | --- | --- | --- |
| 连续 20 张简单图 | 3 次新宿主 | 后两轮 1580 / 1565 | 16710–17047 | 每图只有 3 节点；初始块包含全部 20 图，尾部占位等待明显 |
| 补测：新渲染器、20 图 | 各 1 次 | 1382 | 16512 | SVG 20 张；错误 0 |
| 补测：同一宿主缓存重开 | 各 1 次 | 267 | 413 | SVG 20 张；错误 0 |
| 150 节点链式图 | 1 次 | 1773 | 1816 | 图本身较长；首图约 1.8 s |
| 约 5 MB / 100 张分散图 | 1 次 | 3525 | 5385 | 这里只观察初始挂载图，不代表 100 张已渲染；绝不能称为全图耗时 |

**瓶颈判断：** 新宿主中连续 20 张极小图仍需约 16.7–17.0 s；同一宿主缓存重开只需 413 ms。结合 `DiagramService` 每个任务新建页面、重复装载 Mermaid runtime 并串行运行的实现，主要怀疑初始化与队列开销；这是结合代码与对比结果的推断，尚未做 CPU profile 来精确分摊占比。视口外但仍处于已挂载块内的图也会进入队列。

建议复用已加载的渲染页面、限制并发到 1–2 个工作者、优先当前视口、取消过期任务；缓存保留。首图、当前可见图全部完成、队列末尾必须分别测量。不要直接无限并行渲染。

## 代码、大段落、表格：正文快不能代表大块快

| 场景/实际初始大小 | 样本数 | 激活块 ms | 输入 P95 ms | 最慢输入 ms | 输入期最长主线程任务 ms | 判断 |
| --- | --- | --- | --- | --- | --- | --- |
| code-102400.md / 102474 B | 40 | 216 | 31.8 | 37.8 | 0 | 本样本流畅 |
| code-1048576.md / 1048606 B | 40 | 539 | 356.0 | 453.7 | 223 | 明显卡顿 |
| paragraph-100KB.md / 128020 B | 40 | 453 | 594.5 | 758.4 | 638 | 明显卡顿 |
| table-1000rows.md / 34829 B | 40 | 239 | 71.5 | 117.9 | 69 | 未达 50 ms 目标 |

约 1 MB 代码块打开期还观察到 609 ms Long Task；它的“首屏可编辑 656 ms”并不能消除后续输入卡顿。代码块静态高亮转入编辑后会消失；Tab 会把焦点移到下一个块，详见代码块报告。

**实现原因的推断：** `editor.ts` 在每次 docChanged 时序列化整个活动 EditorView 文档。视口虚拟化解决了大量小块，却未解决单个代码块/段落/表格过大；输入时反复序列化与大范围排版可能共同导致这些长任务，需要进一步 profile。建议保留即时的轻量内容更新，把昂贵序列化移至增量、空闲或保存路径，并明确保存/备份必须等待完成；超大块可提供清晰的降级入口。

## 渲染期间输入与查找/大纲补测

这是额外一次真实宿主诊断，原始数据在 [concurrent.json](concurrent.json)。

- **Mermaid 渲染期间：** 输入开始时 20 图都在等待，结束时 5 图完成、15 图仍等待。120 个键盘字符的 event-to-two-frames P95 为 32.7 ms，最慢 34.7 ms，输入期未观察到 Long Task。因此本样本的主要问题是图表排队等待，未观察到后台图表渲染同时卡住普通正文。
- **常见词查找：** 5 MB 文档搜索 Local，创建 29810 个结果按钮，到观测更新帧约 1346 ms；最长主线程任务 986 ms。
- **修改关键词：** 从上述海量结果切换到不存在的词，记录到 **12107 ms 主线程长任务**。测试控制器从开始填写到更新检查记录了 27895.5 ms，该窗口包含自动化等待、更新与布局，不能全部归因于字符串匹配算法；但 12.1 s 的 UI 主线程阻塞已经独立证实，足以让用户明显感到冻结。
- **大纲：** 创建 29811 个按钮，到两个更新帧约 1047 ms，最长任务 915 ms；而且从已打开的 Find 点击 Outline 后 navigation.hidden=true，内容换成大纲却把面板关掉。

查找/大纲应列为 P0 性能问题：索引可增量或移入 worker，结果应分页或虚拟化，不能挂载近三万个按钮；清空结果不应逐项触发昂贵更新。建议 5 MB、3 万次命中时首批结果 ≤300 ms、所有关键词切换 P95 ≤300 ms、结果 DOM ≤100 项、无 >100 ms 长任务；Find↔Outline 切换应保持面板可见并保留各自查询/展开状态。

## 性能验收门槛

| 项目 | 建议门槛 | 执行口径 |
| --- | --- | --- |
| 1 MB / 5 MB 打开 | 可读 ≤1.5 s / ≤2 s；5 MB 可编辑 ≤3 s | 固定基准机每场景 30 次，按打开 P95 判断 |
| 100 / 500 Include，约 5 MB | 可读 ≤2 s，可编辑 ≤3 s；完整索引 ≤5 s | 分别记录首屏与索引；同语料哈希 |
| 常见段落/代码/表格输入 | P95 ≤50 ms，P99 ≤100 ms | 每种块至少 1000 字符，覆盖中部和末尾、真实 IME |
| 1 MB 单块压力 | 目标 P95 ≤50 ms；未满足前必须明确限制/提供不会冻结页面的降级 | 不能把极端块结果排除后继续宣传任意 5 MB 都流畅 |
| 首次简单 Mermaid | 首图 ≤1.5 s；当前视口所有简单图 ≤2 s | 渲染器进程关闭后开始，20 图队列也要测 |
| 20 张简单图全部完成 | 冷态 ≤5 s；缓存重开 ≤500 ms | 分别报第一张/可见图/全部图，错误为 0 |
| 150 节点图 | 首次 ≤3 s；期间正文输入 P95 ≤50 ms | 图渲染与正文输入同时进行，至少 10 次 |
| 高亮显示 | 可见普通代码块 ≤200 ms；100 KB ≤500 ms | 先显示文字，异步着色；不得阻塞输入 |
| 滚动 | 帧间隔 P95 ≤33.3 ms，无 >100 ms 连续停顿 | 60 s 鼠标滚动，中间区与末尾；同时记录 Long Task |
| 小子文件保存 | <100 KB 子文件 P95 ≤200 ms | 至少 50 次，核对只写目标文件 |
| 发布门禁 | 超阈值让发布失败 | 真实宿主 + 已安装 VSIX；记录硬件、版本、构建哈希、原始数据 |

上表为建议验收目标，不表示已经达成。本轮是开发宿主验证；没有用安装后的 VSIX 重跑全部压力矩阵，没有执行硬件键盘、真实中文 IME 和小时级稳定性测试。
